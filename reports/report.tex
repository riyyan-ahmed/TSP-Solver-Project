\begin{abstract}
\noindent
This report describes the development of a C++ solver for the metric Travelling Salesman Problem. We cover the chronology of the work, the tools we relied on, the structure of the code and the reasons behind the main design choices. At the time of writing, the program reads both TSPLIB formats required by the specification, runs the trivial method and writes tours in the required format. A test suite of 92 cases covers the parser, the graph classes, the tour writer and the compiled executable.
The tours produced for the provided instances were checked with the course solution checker, which accepted them as valid (for example, the trivial tour of \texttt{gr17} has length 4722).
\end{abstract}

\section{Introduction}

The project~\cite{subject} aims to write a program that reads a TSP instance, calculates a Hamiltonian cycle, and prints it out to a file. It is required that the specification contains a build script located at the root of the project, an executable named \texttt{TSPsolver} that reads an instance path, an output path and that may take an optional method name, and an executable named \texttt{tests} that reads an instance path and an output path location. It also corrects the input formats: a list of planar coordinates followed by a lower triangular weight matrix, and the output format - a list of permutations terminated with -1 and \texttt{EOF}.

The grading puts half of the weight on design quality, so we divided the program into small parts with clear responsibilities. Each of instance representation, distance computation, parsing, validation of tours and output is implemented in a separate class and each has tests.

This report covers the mid-term checkpoint, for which the program must support the trivial method only. For the final submission, in addition to the same parser, graph and output classes, the Held-Karp algorithm will be included, as well as a third algorithm of our own choice.

\subsection{Setting up the project}

We split up the work on 23 September so we began implementing it locally, and on 30 September, we pushed our first work to the remote repository. This project is based on a template provided in the course, which has already separated headers, sources and tests. This layout was retained. Together with the code for the lower triangular matrix format, we wrote the first version of the parser on 1 October together with the empty files for the rest of the architecture to fix the structure before the algorithm existed.

The header of the TSPLIB had to be taken care of a little bit. The order of the entries is arbitrary, there may be no space in the files before the separator, some entries (e.g. comments) may include another separator within the value, and there may be any number of files. Thus, each line of the header is split only at the first separator, both the left and right parts of the split line are trimmed, and entries that are not required are discarded.

\subsection{Matrix instances and the first solver}

By 10 October the parser was able to deal with the lower triangular format and the trivial method existed. Most of the work in this phase was due to two properties of the provided files. First, the matrix may not be written row-wise, that is, one row per line, so it's read as a stream of integers and reconstructed based on the dimension. Second, one instance (\texttt{dantzig42}) is followed by a display data section containing coordinates which are only intended for display. This section needs to be recognised explicitly since the parser otherwise rejects data after the matrix. It delays to the next key word, and ignores any following information.

\subsection{Command line and coordinate instances}

On 12 October we wrote the command line handling and connected the parser, the solver and the writer in \texttt{main}, so that the complete pipeline ran for the trivial method on the matrix instances. We lost the build script for a few minutes during a cleanup, and restored that same night to see how easy it can be to mess up the single requirement that is checked first. We then added the coordinate format in three small steps, the graph class, the Euclidean distance and the parsing of the coordinate section.

Since nothing forces the lines of a coordinate file to be sorted, each city is stored at the position given by its identifier, and the identifiers are kept so that the tour file uses those of the input (Section~\ref{sec-parsing}).

\subsection{Review and tests}

We reviewed code with the specification and wrote the test suite (on 14 October). Our manual runs did not detect some of the defects the review found: the test files were ignored by Git, an out of range matrix index caused undefined behaviour, the build did not yield \texttt{build/TSPsolver} (challenges 3 and 4 in Table~\ref{tab-challenges}) and the coordinate parser accepted data after \texttt{EOF}. The most informative one had to do with the tour writer. It opened the output file, which will delete the file's contents when reading that file, before verifying that the tour is valid, so a bad solver would have deleted a previous result. The check is now performed before opening a file, and a test ensures that if an invalid tour is entered, no changes are made to an existing file.

The choices we make for these points are discussed and the alternatives left in the language by the subject are discussed in Section~\ref{sec-limits}.

It was easy to write, but limited the future algorithms to one kind of storage, lost coordinates of coordinate files and had no natural site for the distance computation. For this reason we opted for a small class hierarchy (commit \commit{e8f5266}) similar to the one used for the graph library of the object oriented programming lab~\cite{tp4}. \subsection{Representation of an instance}

An instance consists of a name, the identifiers of the cities as given in the file and a graph. The graph is an abstract class and it has two operations – one returns the number of vertices, the other returns the weight of a given edge, and a third to calculate the length of a tour. This function is placed in the base class to ensure that all graph and all solver compute a tour in the same manner.

The lower triangle of this matrix is saved in the matrix graph. The graph is complete, thus an adjacency list would contain as many $n(n-1)/2$ edges, and would require a longer time to find an edge, while the graph would be stored as a dense matrix, and would answer \texttt{weight(i,j)} in constant time. The memory requirement of coordinate graph is linear in the number of cities, because it keeps only the points, it calculates all the distances when needed. Both classes have the same interface, so a solver is written once and can be used with both, and both check their inputs and indices and throw exceptions if they are bad, so that a bad input or bad index does not result in undefined behaviour.

In the program, vertices are numbered starting from 0. They're only converted back to the identifiers of the file at the tour writer, taking one of the algorithms with them.

\subsection{Parsing}\label{sec-parsing}

The parser is broken into two phases. The header stage reads the lines of \texttt{key : value} till it encounters the keyword at which the data section begins and verifies the presence of the name, the type and the presence of a positive dimension. The keyword then is used to select the data stage, each of which is implemented in a separate file for each format. In addition, the matrix stage needs explicit weights in the matrix format with a row of zeros in the lower diagonal format, because otherwise they will be read incorrectly. The identifier is supplied from 1 to the coordinate stage (for TSPLIB files) or from 0 to the coordinate stage (for course generator); each city is placed on the coordinate stage at the position specified by its identifier.

The parser can be fed anything other than a file path, allowing the tests to provide it with small malformed inputs as strings. One parser can read several instances, each call resets the state of the parser. Errors are reported as exceptions, with the name of the error as a message, and only at the entry point. Exceptions were selected because they are not amenable to local correction when a parsing failure occurs and because they maintain the readability of the normal path of the code.

The parser is strict about content that changes the meaning of the instance (negative weights, a non zero diagonal, duplicate identifiers, missing or trailing data) and tolerant about the rest, such as spacing around separators, blank lines, Windows line endings and unknown header entries.

\subsection{Solvers}

A solver is any class that implements a common interface with a single function, which takes an instance and returns a tour represented as a vector of vertex indices. The trivial method returns the vertices in increasing order of their index, which is also the order of their identifiers. Because a solver only sees the graph interface and returns a plain vector, it does not depend on the input format or on the output format. Adding a method means adding one class and one line in the function that maps a method name to a solver.

\subsection{Writing tours}

The tour writer converts a tour to the output format. Before writing, it checks that the tour is a permutation of all vertices, so that no solver can produce an output file that violates the specification. The output name is derived from the instance name by replacing a trailing extension, and only a trailing one. A second overload writes to any output stream, which is what the tests use to compare the exact text of the output with the example of the specification. Appendix~\ref{app-tour} shows a complete output file.

\subsection{Entry point and error handling}

The entry point reads the arguments, parses the instance and then calls the solver given in the argument and writes the tour. It requires two arguments: the instance and the output file, and it can take any number of times at the command-line the option \texttt{-m} (method name). If any other option is specified, it is a missing or extra path, a \texttt{-m} without a value, and a return of non zero status, the method name is checked before reading the instance, and a message is printed with the usage. All errors thrown by the library, both in parsing and in solving or even writing, are exceptions that are derived from the standard exception class. The entry point captures it where it is seen, prints the message from the entry point to the error stream and returns the same status. The library classes do not print anything themselves so they are reusable and the tests check the errors without parsing the text.

\section{Key parts of the code}\label{sec-code}

This section shows the short pieces of code that carry the main design decisions. Documentation comments are left out to save space, and some lines are omitted where marked.

\paragraph{The graph interface.} Every solver works only with this abstract class, so it is independent of the file format.
\begin{lstlisting}
class Graph {
    public:
        virtual ~Graph() = default;
        virtual std::size_t size() const = 0;
        virtual double weight(std::size_t i, std::size_t j) const = 0;
        double tourLength(const Tour& tour) const;
};
\end{lstlisting}

\paragraph{Reading the lower triangle.} Weights are read one by one, whatever the line breaks, and each value fills both halves of the symmetric matrix.
\begin{lstlisting}
for (int i = 0; i < dimension; i++) {
    for (int j = 0; j <= i; j++) {
        int weight;
        if (!(input >> weight)) {
            throw std::runtime_error("Missing or invalid integer distance");
        }
        // ... checks for negative weights and a non zero diagonal ...
        distances[i][j] = weight;
        distances[j][i] = weight;
    }
}
\end{lstlisting}

\paragraph{Identifiers starting at 0 or 1.} All lines are read first. The smallest identifier tells whether the file counts from 0 (course generator) or from 1 (TSPLIB), and each city is then stored at the position given by its identifier.
\begin{lstlisting}
const int firstId = (*std::min_element(ids.begin(), ids.end()) == 0) ? 0 : 1;

for (int i = 0; i < dimension; ++i) {
    const int index = ids[i] - firstId;
    if (index < 0 || index >= dimension) {
        throw std::runtime_error("City id out of range");
    }
    if (cityIds[index] != -1) {
        throw std::runtime_error("Duplicate city id");
    }
    cityIds[index] = ids[i];
    coordinates[index] = points[i];
}
\end{lstlisting}

\paragraph{The trivial method.} Since the parsers store the cities in increasing order of their identifiers, visiting the indices in order gives the tour $1 \rightarrow 2 \rightarrow \dots \rightarrow n$.
\begin{lstlisting}
Tour TrivialSolver::solve(const TspInstance& instance) const {
    Tour tour;
    for (std::size_t i = 0; i < instance.size(); i++) {
        tour.push_back(i);
    }
    return tour;
}
\end{lstlisting}

\paragraph{Writing the tour.} The tour is validated before the file is opened, so an invalid tour never empties an existing file.
\begin{lstlisting}
void TourWriter::write(const TspInstance& instance, const Tour& tour,
                       const std::string& filePath) const {
    checkIsPermutation(tour, instance.size());

    std::ofstream output(filePath);
    if (!output.is_open()) {
        throw std::runtime_error("Cannot open output file: " + filePath);
    }
    write(instance, tour, output);
    // ... check that writing succeeded ...
}
\end{lstlisting}

\section{Build and run}\label{sec-run}

The project is built from its root with a single command, which creates \texttt{build/TSPsolver} and \texttt{build/tests}. GoogleTest is downloaded the first time the project is configured.
\begin{lstlisting}[language=bash]
bash build-TSPsolver.sh
\end{lstlisting}

The solver takes the instance path, the output path and an optional method. Without \texttt{-m}, the trivial method is used.
\begin{lstlisting}[language=bash]
./build/TSPsolver TSP-instances/lower_diag/gr17.tsp gr17.tour
./build/TSPsolver TSP-instances/coord/berlin52.tsp berlin52.tour -m trivial
\end{lstlisting}

The tests are run with:
\begin{lstlisting}[language=bash]
./build/tests
\end{lstlisting}

\section{Limitations and decisions}\label{sec-limits}

The subject leaves some points open. Table~\ref{tab-decisions} lists the decisions we took.

\begin{table}[htbp]
\centering\small
\begin{tabularx}{\linewidth}{@{}L{4.6cm} Y@{}}
\toprule
Point & Decision \\
\midrule
\texttt{EOF} keyword & Optional, since \texttt{pr1002} has none; any data after it is rejected \\
\texttt{DISPLAY\_DATA\_SECTION} & Skipped, since it only holds drawing coordinates (\texttt{dantzig42}) \\
City identifiers & May start at 1 (TSPLIB) or at 0 (course generator); the tour file uses the identifiers of the input \\
\texttt{NAME} of the tour file & Instance name with a trailing \texttt{.tsp} removed, followed by \texttt{.tour} \\
Default method & Trivial \\

\bottomrule
\end{tabularx}
\caption{Decisions on points left open by the subject.}
\label{tab-decisions}
\end{table}

The major constraint is the final decision. The distance functions defined in TSPLIB are: rounded Euclidean (\texttt{EUC\_2D}), geographical (\texttt{GEO}) and pseudo Euclidean (\texttt{ATT}). For all of our files, our coordinate graph is designed with a plain Euclidean distance but not rounded distances. The tours written by us are not affected, as it is a trivial method that isn't based on distance, but the lengths of the tours that our program produces would differ from the official ones. The difference is small for \texttt{EUC\_2D} files (\texttt{eil76}: 1974.7 vs. 1969), but large for the other types of file because \texttt{GEO} coordinates are latitudes/longitudes and \texttt{ATT} uses a scaled distance (\texttt{burna14}: 42.5 vs. 4562; \texttt{att48}: 157\,530 vs. 49\,840). This should be corrected before comparing the lengths of the following methods with published optima.

The second drawback is that this is the trivial solution and does not attempt to find a short tour, as it is designed to test the pipeline from parsing to output (Table~\ref{tab-quality}).

\section{Future work}\label{sec-future}

For the final submission we plan the following steps, in this order.
\begin{enumerate}
  \item \textbf{TSPLIB distances.} Read \texttt{EDGE\_WEIGHT\_TYPE} and give the coordinate graph the matching distance function (\texttt{EUC\_2D}, \texttt{GEO}, \texttt{ATT}), and check the lengths against the course checker.
  \item \textbf{Held-Karp algorithm}~\cite{heldkarp}. Dynamic programming over subsets with a bitmask, plus backtracking to recover the tour. Its table needs $n \cdot 2^{n-1}$ values, about 84\,MB for $n = 20$ and 3.4\,GB for $n = 25$, so the solver will refuse instances above a size limit instead of running out of memory. It must give the known optima, for example 2085 on \texttt{gr17} and 3323 on \texttt{burma14}.
  \item \textbf{Third method.} A heuristic for large instances, for example a nearest neighbour tour improved by 2-opt, to be discussed with the teacher before coding.
  \item \textbf{Measurements.} Time the solving step alone inside the program, print the tour length, and repeat Section~\ref{sec-perf} for the three methods.
\end{enumerate}

\section{Reflections}

The most useful decision of the first weeks was to fix the structure of the code early. It allowed us to add the second input format in three small commits without touching existing code. The review of 14 October was less comfortable, since it showed that several parts we considered complete had behaviour that we had never exercised. The problems with the output file and the matrix accessor would not have appeared in normal use, and we only found them because the tests supplied inputs that a careful user would not. If we repeated the project, we would write the tests of each component at the same time as the component.

Two further lessons came from the last days before the checkpoint. First, a program that works on our machines is not enough: the build has to be checked exactly as the grader will run it, from a clean copy and with the commands of the subject, which is how we found that the executable had the wrong name and location. Second, working on two separate branches for two weeks made the final merge harder than it needed to be. Agreeing on the shared classes first helped, but merging more often would have shown integration problems earlier.
